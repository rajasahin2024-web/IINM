INTRO

The Zero to Launch Promise

Theory goal: reader understands exactly what they will own in 7 days and believes they can do it without coding.
  • What you'll hold at the end: a live web app + a way to sell it + the vocabulary to talk about it like a builder.
  • Why AI agents changed who gets to build software — the shift from "learn to code for years" to "direct an agent this week".
  • The stack preview: your app is built the same way professionals build it — React (screens), FastAPI (logic), PostgreSQL (memory). The agent writes the code; you learn to run the project.
  • Who this book is for — students, business owners, working professionals with zero coding background — and who it isn't for.
  • The 7-day map: what happens each day, and why the order matters.

Part 1 · Foundation

Days 1–3

CH 1

How AI Builds Software Now

Day 1
Theory goal: reader understands the agentic shift and their new role — confidence, not syntax.
  • Chatbot vs. AI agent: a chatbot answers questions; an agent does the work — plans, writes files, runs commands, checks its own output. What "agentic" means in plain words.
  • What agents are good at — and where they fail: fast at standard patterns, weak at taste and judgement; why honesty here builds trust for the whole book.
  • Your new job title — Product Owner, not programmer: you decide what gets built and whether it's good enough; the agent handles the how.
  • Three real examples of software built this way: a business site, a working web app, a paid client project.

"Chatbot vs. Agent — Who Does the Work?"

Right: user tells an agent the same thing → agent draws a plan, creates files, runs commands, hands back a working folder. CH 2

Your Toolkit: What's in the Box and Why

Day 1
Theory goal: reader can name every tool in the stack, what job it does, and how talking to an agent actually works — setup mechanics stay out of the chapter.
The tools and their jobs
  • The AI agent tool — your builder; what it can and can't decide for you.
  • React — builds the screens the user sees and clicks.
  • FastAPI — the backend brain: login, orders, payments, all the logic.
  • PostgreSQL — the database that remembers users, products, orders (free tier: Neon/Supabase).
  • Vercel + Render — the free hosting pair that puts the app on the internet.
  • Razorpay — how money enters the app (UPI/cards, Indian market).
The economics
  • The free-tier map: what "₹0/month to start" actually means — which tool is free at what limit, and where the first rupee eventually goes.
How communication with an agent works (theory)
  • The 3-line prompt formula: context (what exists), instruction (what to change), finish line (how you'll know it worked).
  • The Prompt Word Bank: why precise words get precise results — nouns (component, endpoint, router, table, index), verbs (add, fix, refactor), quality words (responsive, minimal, mobile-first), and finish lines ("done when the form saves and shows success").
  • Why the agent writes better React/FastAPI/Postgres than anything else — most tutorials and training examples exist for this stack; choosing popular tools = choosing a better-trained agent.
The one design
"The Workshop Wall — Six Tools, Six Jobs"

What it shows: one labelled illustration of a workbench wall: six tools hanging in a row, each with its name and a one-line job — Agent (the builder), React (the screens), FastAPI (the brain), Postgres (the memory), Vercel/Render (the shopfront on the internet), Razorpay (the cash counter).

Why it teaches: six abstract tool names become six visible objects with jobs — the reader memorizes the stack by picture, not by list.

CH 3

Speak Like a Builder: The Anatomy of a Web App

Day 2
Theory goal: reader can name every part of a web app, what runs where, and how the parts talk — every name drawn from our real stack. The vocabulary spine of the whole book.
The three layers
  • Frontend — what the user sees (React): every piece of UI is a component — a reusable block; props are the settings you pass it; JSX is the file format mixing layout + logic.
  • Backend — what runs behind the screen (FastAPI): the server that answers requests; main.py starts it, routers group related endpoints (auth.py, products.py, orders.py), models define data shape.
  • Database — the app's memory (Postgres): tables of users/products/orders; a row is one record, a column one fact; SQL is the language you ask it questions in; an index is what makes search instant.
What the user-facing side looks like
  • The 6 types of UI you'll actually use: landing page, multi-page site, form & list, dashboard/admin, e-commerce catalog + checkout, mobile-responsive layout — what each is and when to pick which.
  • UI building blocks by name: navbar, hero, card, table, form field, modal, button states (hover/disabled/loading) — the words that make prompts precise.
How the layers talk
  • REST API — the conversation between frontend and backend: an endpoint is a URL with a job; GET = read, POST = create, PUT/PATCH = update, DELETE = remove; request → response in JSON, with one worked example ("click Pay → the React page POSTs the order to /api/orders").
  • Authentication — who are you: signup/login, sessions & tokens; JWT as a wristband (server stamps it at login, browser shows it every request); OTP and Google login (OAuth); Firebase Auth as the done-for-you option; protected vs. public pages.
  • Optimization — fast and findable: image compression, lazy loading, caching, CDN, database indexing, minified code, SEO basics — each as a one-line "what it is + when it matters".
The one design — the book's recurring visual
"The Anatomy Map"

What it shows: one labelled end-to-end diagram — User → React frontend → REST API → FastAPI backend → PostgreSQL database — with each layer's contents drawn inside its box (components in React, routers in FastAPI, tables in Postgres) and arrows labelled GET/POST/JSON. Every term in the chapter appears somewhere on this one page.

Why it teaches: this single picture IS the chapter. It is reprinted at the start of later chapters as the reader's compass — the most important sketch in the book.

CH 4

The Stack, Up Close: React + FastAPI + PostgreSQL

Day 3
Theory goal: reader knows what each tool does, why we chose it, the handful of commands the agent runs, the project folder map, and how every module (login, search, checkout) is wired across the three layers — in small labelled pieces.
Part A — Why this stack (the honest reasons)
  • Why React: reusable components; the most-used frontend library in the world → biggest job market, most tutorials, most AI-training examples (agents write React best).
  • Why FastAPI: Python reads like English; auto-builds a clickable test page at /docs — test the API in a browser without code; catches its own mistakes via type hints.
  • Why PostgreSQL: free forever, owned by no company, trusted from startups to banks; real SQL — the skill that transfers to every job; built-in search power (indexes, full-text).
  • "Why not the others?" box: plain HTML vs React; Express/Django vs FastAPI; Firebase/MongoDB vs Postgres — honest one-line tradeoffs.
Part B — The Command Sheets (recognize, don't memorize)
  • React commands the agent runs: npm create vite@latest, npm install, npm run dev, npm run build — each with its plain-English meaning.
  • FastAPI commands: pip install fastapi uvicorn, uvicorn main:app --reload, pip freeze > requirements.txt, and the /docs test page.
  • Postgres commands: CREATE TABLE, INSERT, SELECT ... WHERE ... ILIKE, CREATE INDEX, the Neon/psql console — each as "what the agent is doing" in one line.
Part C — The Project Map (the directory, explained)
  • The full folder tree: frontend/src/components + pages + App.jsx, backend/main.py + routers/ + models.py + database.py, database/schema.sql + seed.sql — every file named with the reason it exists.
Part D — The Module Map (features wired across 3 layers)
  • Login/Signup: Login.jsx → auth.py POST /auth/login → users table — powered by JWT (or Firebase Auth for done-for-you OTP).
  • Product catalog: Home.jsx + ProductCard → products.py GET /products → products table — CRUD + pagination explained.
  • Search: search bar → search.py GET /search?q= → ILIKE + index, then full-text (tsvector) when the catalog grows.
  • Cart & checkout: Cart.jsx → orders.py POST /orders → orders + order_items — the webhook: Razorpay calls YOUR endpoint to confirm; never trust the browser.
  • Admin panel: Admin.jsx → protected endpoints → all tables — a protected route demands a valid JWT with the admin role.
Part E — How search actually works
  • The request walkthrough: "cotton kurta" → GET /search?q= → SQL ILIKE query — what happens at each hop.
  • Sequential scan vs. index: without an index Postgres reads every row (fine at 50, painful at 50,000); with CREATE INDEX it jumps straight to matches — the book-index analogy.
  • When ILIKE isn't enough: full-text search (tsvector) — matching meaning, ranking results, handling typos.
The one design
"The Module Wiring Diagram — One Feature Across Three Layers"

What it shows: the Anatomy Map zoomed into ONE feature — Login — drawn as a journey: the Login.jsx form → arrow labelled POST /auth/login → auth.py router → arrow into the users table → back-arrow labelled "JWT wristband issued". The other four modules appear as faded rows beneath, same shape.

Why it teaches: the reader sees the pattern once — every feature is the same three-layer trip — then understands all five modules without re-learning anything. (The folder tree and command sheets print as tables beside it; the wiring diagram is the page's teaching sketch.)

CH 5

Pick a Winner: Your First App Idea

Day 3
Theory goal: reader understands what makes an idea buildable and sellable in 7 days — and can filter their own.
  • The v1 rule: one user, one problem, one page that solves it — why small first versions win.
  • The 5 idea templates that sell in India: local business site + booking, catalog store, landing + lead form, portfolio, booking/service app — each mapped to its UI type (Ch 3) and its module subset (Ch 4).
  • The competitor scan concept: 10 minutes of looking at who already sells this — what to note (price, look, what's missing).
  • The scope filter: if it takes more than 7 days, cut it in half — how to halve an idea without killing it.
The one design
"The Idea Funnel"

What it shows: a funnel graphic — a cloud of ~10 raw ideas at the top ("build the next Flipkart!", "an app for everything") passing through three labelled gates: one user one problem? → fits a template? → buildable in 7 days? — with one clean idea coming out the bottom, tagged with its UI type and module list.

Why it teaches: "scope" is an abstract rule; the funnel turns it into a machine the reader can run any idea through.

Part 2 · Build

Days 4–6

The theory of directing an agent: plan first, then iterate — every concept named with the Ch 3–4 vocabulary.

CH 6

Plan Before You Prompt

Day 4
Theory goal: reader understands why a written spec beats blind prompting, and what a good spec contains.
  • Why prompting without a plan fails: the agent guesses at every gap — structure in, structure out.
  • What a spec is: a one-page brief — user, problem, pages (React), features/modules (the Ch 4 Module Map), what data lives where (Postgres tables).
  • The module checklist concept: every app idea is a subset of the 5 modules — "catalog + search + checkout, no login yet" is a complete sentence to an agent.
  • How the agent reads a spec: it generates the folder structure, plans files, and works the list — which is why asking for the Ch 4 directory by name gets a professional result.
The one design
"Spec In, Structure Out"

What it shows: left panel — a messy paragraph of wishes going into the agent, producing a jumbled pile of files. Right panel — the same wishes arranged as a spec card (user / pages / modules / tables), producing the neat Ch 4 folder tree.

Why it teaches: the single most valuable build habit — write the spec first — shown as cause and effect.

CH 7

The Build Loop: Prompt → Check → Fix

Day 4
Theory goal: reader understands the iteration cycle and the debug vocabulary that makes fixes fast.
  • Small prompts beat big prompts: one component or one endpoint per round — why small changes are checkable and big ones aren't.
  • The error loop: paste the error, state expected vs. actual, name the part — the three ingredients of every good fix request.
  • Debug vocabulary that halves fix time: name the layer + the file — "the Login.jsx page" (React), "the /auth/login endpoint in auth.py" (FastAPI), "the users table" (Postgres).
  • Reading the Command Sheets live: when the agent runs npm run dev or uvicorn main:app --reload, what's actually happening — boss, not passenger.
  • "The agent is stuck" playbook: reset the conversation, simplify the request, split the task — when to use which.
  • The checkpoint habit: saving working versions before each change — the idea of git, named not taught.
The one design
"The Loop"

What it shows: a circular diagram — Prompt (small) → Agent builds → Check → Works? → yes: next piece / no: Error Loop (paste error, expected vs actual, name the file) → back to Check. A side callout shows the three escape hatches: reset, simplify, split.

Why it teaches: building with an agent feels chaotic until you see it's one repeatable loop — the sketch turns "it broke!" panic into "I'm at the Check step" calm.

CH 8

Make It Look Real

Day 5
Theory goal: reader understands what separates a demo-looking app from an agency-looking one — the vocabulary of polish.
  • The polish checklist: name, colors, fonts, spacing, mobile view — and the word responsive: what it means and why it matters in India (most traffic is phones).
  • UI states that signal quality: hover, loading, empty, error — the states users subconsciously judge.
  • Copy that sells: the headline formula (who + outcome + time) and button text that says what happens next.
  • Free assets done right: images, icons, AI-generated logo — and image compression as the reader's first optimization concept.
  • The "₹50,000 agency look": the 5 small details that signal professional work — consistent spacing, one accent color, real photos, aligned buttons, no lorem ipsum.
The one design
"Before / After — The Same Page, Twice"

What it shows: one phone frame split in two — left: the same store page looking like a default demo (grey, crowded, placeholder text); right: after the polish pass (one accent color, breathing space, real headline, neat buttons). Five numbered callouts mark exactly what changed.

Why it teaches: "polish" stops being vague — the reader sees the five differences and knows the words to ask for each.

CH 9

Working Features: Login, Data, Payments

Day 6
Theory goal: reader understands how the three "real" features actually work end-to-end — stored data, logged-in users, collected money — and can say which ones their app needs.
  • The anatomy revisited: circle your app's pieces on the Anatomy Map + Module Map — pages, routers, tables, endpoints.
  • How storing data works: schema.sql is the app's skeleton — the agent writes the CREATE TABLEs, you approve tables in plain English; seed.sql fills sample rows.
  • Forms that do something: a React form POSTing to a FastAPI endpoint — contact, booking, order forms are all the same pattern.
  • Authentication in practice: JWT via auth.py vs. Firebase Auth for done-for-you OTP — which to pick when, and what "protected pages" means.
  • Search in practice: the index is what makes it instant — optimization understood as a decision, not a chore.
  • Taking money: Razorpay payment link vs. full checkout, and the webhook concept — Razorpay calls YOUR endpoint to confirm payment; the browser saying "paid" is never proof.
The one design
"The Two Trust Flows"

What it shows: two short sequence strips on one page. Strip 1 — Login: user enters password → server checks users table → issues JWT wristband → browser shows wristband on every later request → protected page opens. Strip 2 — Payment: customer pays on Razorpay → Razorpay calls your /webhook endpoint → order row marked "paid" → confirmation page. A big red cross on the wrong path: "browser says paid" ≠ paid.

Why it teaches: JWT and webhooks are the two concepts everyone fears — as drawn stories they're just wristbands and phone calls.

CH 10

Go Live: Deploy & Domain

Day 7
Theory goal: reader understands what "deploying" actually means, where each layer lives, and what a domain adds.
  • What "deploy" means: your code moves from your machine to a server that never sleeps — hosting, build command (npm run build), environment variables (where the JWT secret and database URL live), HTTPS — each in one line.
  • Where each layer goes: React frontend → Vercel, FastAPI backend → Render (free tier), Postgres → already lives on Neon/Supabase — why the three deploy separately but work as one app.
  • Domains: what a domain is, buying on GoDaddy/Hostinger (~₹500–800/yr), connecting it, HTTPS/SSL.
  • The speed pass: what Lighthouse measures, compressed images, mobile load — the launch-speed concept.
  • The launch checklist: the 12 things to verify before sharing the link — and why announcing publicly is part of launching.
The one design
"The Deployment Map"

What it shows: the Ch 4 folder tree on the left with three arrows leaving it — frontend/ → Vercel cloud, backend/ → Render cloud, database/ → Neon — all three merging under one roof labelled "yourdomain.com + HTTPS lock", with a customer's phone connecting to the roof.

Why it teaches: deployment feels like magic until you see it's just three folders moving to three free hosts under one name.

CH 11

Test Like a Customer

Day 7
Theory goal: reader understands how to check their own product the way a buyer will — and where the stack-specific checks hide.
  • The 20-point QA mindset: mobile view, speed, broken links, working forms, payment flow — checking as a customer, not as the builder.
  • The stack checks: does login return a JWT? does search hit the index? does the Razorpay webhook fire? — how each maps back to the Module Map.
  • Making the agent test its own work: the self-review concept, and FastAPI's /docs page as the reader's personal click-test lab — no code needed.
  • The friend test: watch someone use it without explaining anything — why silence is the test.
The one design
"The Customer Test Path"

What it shows: a shopper's footprints walking through the app — Home → Search → Product → Cart → Pay → Confirmation — with checkpoint flags at each step ("did search feel instant?" / "did payment confirm via webhook?") and the three stack checks marked as hidden inspection hatches under the path.

Why it teaches: QA stops being an intimidating checklist and becomes a walk the reader has already taken a hundred times as a customer.

CH 12

Your First Paying Customer

Day 7+
Theory goal: reader understands who buys websites, what to charge, and how to talk about their skills in builder language.
  • Who buys: local shops, clinics, tutors, gyms, restaurants — the "no website / bad website" hunt and why local beats online freelancing for a first sale.
  • Pricing your first project: the ₹5k–15k starter ladder and how to quote — priced by modules, not by hours.
  • Sounding like a pro: quoting in builder terms — "responsive React site + booking form + admin panel, database-backed" — the Ch 3–4 vocabulary as sales language.
  • The outreach channels: WhatsApp message, walk-in pitch, referral ask — how each works and why WhatsApp wins in India.
  • Handling the two objections: "how much?" and "let me think about it" — the theory of answering without discounting yourself.
The one design
"The Local Opportunity Map + Pricing Ladder"

CH 13

Deliver, Get Paid, Repeat

Ongoing
Theory goal: reader understands the full client-project lifecycle and the retainer model — a business, not a hobby.
  • The client workflow: advance → build → feedback round → final payment → handover — and why the advance exists (commitment, not greed).
  • Monthly retainers: maintenance at ₹1k–3k/month — the compounding trick: 10 small clients = salary-level income.
  • The portfolio page: your deployed apps are your sales pitch — why a live link beats a resume.
  • When to level up: multi-agent builds, real Postgres design, auth at scale, team/agency workflows — what structured training adds (the honest bridge to the course).
The one design
"The Client Flywheel"

What it shows: a circular flywheel — Advance → Build → Feedback → Final payment → Handover → Happy client → Referral/Retainer → next project — with a small side-gear showing retainers compounding (1 client ₹2k/mo → 10 clients ₹20k/mo).

Why it teaches: freelancing looks like a series of one-off gigs; the flywheel shows it as a machine that speeds up with every delivery.
